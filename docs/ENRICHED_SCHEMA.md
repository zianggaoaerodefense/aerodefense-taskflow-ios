# Daily Workflow App — Enriched Task Schema

This document describes the enriched task schema, grouping views, import format,
and security model introduced in the `enriched_task_schema` migration.

---

## Enriched Task Fields

| Field | Type | Description |
|---|---|---|
| `source` | enum | Where the task came from (see Supported Sources) |
| `source_type` | text | Sub-type of source (e.g. `github_pr`, `github_issue`) |
| `source_ref` | text | External ID for deduplication (e.g. PR number, Jira issue key) |
| `source_title` | text | Human-readable source title |
| `source_url` | text | Link to the original item |
| `last_source_at` | timestamptz | When the source item was last active |
| `task_category` | enum | Action type (see Supported Categories) |
| `task_subcategory` | text | Optional sub-category |
| `workflow_name` | text | Denormalized workflow name for grouping |
| `project_name` | text | Project or product area |
| `requester` | text | Who requested the work |
| `owner` | text | Who owns completion |
| `tags` | text[] | Free-form tags for boosting/filtering |
| `group_keys` | jsonb | Pre-computed grouping keys (by_source, by_action, …) |
| `metadata` | jsonb | Source-specific structured data |
| `urgency_score` | integer | Computed urgency (0–140) |
| `importance_score` | integer | Computed importance (0–100) |
| `duplicate_check_note` | text | Note left when a duplicate was detected |

Existing fields (`title`, `description`, `priority`, `status`, `due_at`,
`workflow_id`, `summary_id`, `snoozed_until`, `source`, `created_at`,
`updated_at`) are unchanged.

## Supported Sources

| `source` value | Display label | Notes |
|---|---|---|
| `email` | Email | Set `source_type=external` for customer email |
| `slack` | Slack | Set `source_type=dm` or `mention` |
| `calendar` | Calendar | Meeting prep or follow-up |

## Grouping Views

The mobile app supports 7 grouping dimensions. Each view shows the same task
list but groups it differently. A task appears in exactly one group per view.

| View | Groups by | Sorted by |
|---|---|---|
| Time | Overdue / Today / Tomorrow / This Week / Later / No Date | Time bucket order |
| Source | Email / Slack / GitHub PR / Jira / etc. | Open count desc |
| Action | Review / Respond / Implement / etc. | Open count desc |
| Workflow | Workflow name or "Uncategorized" | Open count desc |
| Project | Project name or "Uncategorized" | Open count desc |
| Requester | Who asked for the work | Open count desc |
| Priority | Critical / High / Medium / Low | Priority order |

Within each group, tasks are sorted by:
1. Status (open → in_progress → waiting → done)
2. Urgency score descending
3. Due date ascending (nulls last)
4. Priority (critical → high → medium → low)
5. `last_source_at` descending
6. `created_at` descending

## Group Keys

The `group_keys` JSONB column stores pre-computed grouping values:

```json
{
  "by_source": "GitHub PR",
  "by_action": "Review",
  "by_workflow": "Expo Mobile App MVP",
  "by_project": "Daily Workflow App",
  "by_time": "Today",
  "by_requester": "Codex",
  "by_owner": "user"
}
```

These are generated automatically at import time if the agent does not include them.

## Urgency Score

`urgency_score` is computed from:

| Factor | Score |
|---|---|
| Priority: critical | +50 |
| Priority: high | +40 |
| Priority: medium | +20 |
| Priority: low | +5 |
| Due: overdue | +50 |
| Due: today | +40 |
| Due: tomorrow | +30 |
| Due: this week | +15 |
| Source: calendar | +25 |
| Source: github_pr | +20 |
| Source: slack DM/mention | +20 |
| Source: customer email | +25 |
| Source: jira blocker | +30 |
| Tags/metadata: production/deployment/customer/proposal/demo | +25 |

Context boosts are capped at +50. Maximum total is ~140.

## Duplicate Avoidance

Before inserting a task, the import service checks for likely duplicates for
the same user.

**Strong duplicate** (checked when `source_ref` is present):
- Same `user_id` + `source` + `source_ref`
- Status is `open`, `in_progress`, or `waiting`

If a strong duplicate is found:
- The existing task is updated with newer `source_title`, `source_url`,
  `last_source_at`, `urgency_score`, `group_keys`, `metadata`, and `description`
- No new task row is created
- A `task_events` row records the update for the audit trail
- `duplicatesSkipped` count is returned to the UI

---

## Security Notes

- `user_id` is always taken from the authenticated Supabase session — never from the imported JSON.
- The forbidden-key scan rejects any payload containing `api_key`, `token`, `password`, `secret`, `jwt`, `cookie`, or `credentials` at any nesting depth.
- `metadata` fields with credential-like key names are silently stripped rather than rejected, so useful context is preserved while secrets are not stored.
- All Supabase writes use the anon key + user JWT; RLS policies enforce that each row belongs to the authenticated user.
- No service role key is used in app code. Edge Functions use the service role key server-side only.
- OAuth tokens for external integrations (Gmail, Slack, Jira) are stored in Supabase Vault, not in any app table.

## Migration

Migration file: `supabase/migrations/20260521000000_enriched_task_schema.sql`

The migration is safe and idempotent:
- All new columns use `ADD COLUMN IF NOT EXISTS`
- The `source` CHECK constraint is dropped and replaced with an expanded version that includes both legacy and new values
- Existing data is preserved — no columns are dropped or renamed
- New array columns default to `{}`; new JSONB columns default to `{}`
